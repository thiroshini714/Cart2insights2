# Cart2Insights: Decoding E-Commerce Performance

An end-to-end e-commerce analytics solution: **Python · Pandas · SQL (MySQL / SQLite) · SQLAlchemy · SciPy · Streamlit**.
Raw CSVs are validated, cleaned, stored in a relational database, enriched with business features, analysed
(EDA + hypothesis tests) and explored through an interactive dashboard that also generates
*Observation → Interpretation → Business impact* insights.

> **Status of this repository.** The real Cart2Insights dataset was **not** available when this project
> was built (the brief only links to it). The code was developed and tested on **synthetic test data**
> generated by `scripts/make_synthetic_data.py`. Therefore **this README contains no business findings**.
> Run the pipeline on the real CSVs and your findings are written to `reports/business_insights.md`
> automatically. See [Testing](#testing) for exactly what was and was not verified.

## Objective

Analyse orders, products, sellers, payments, deliveries and reviews to answer questions on sales,
customers, products, sellers, payments, delivery performance and customer satisfaction, and turn the
answers into actionable recommendations.

## Setup

Requires Python 3.10+ (developed on 3.12).

```bash
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                 # Windows: copy .env.example .env
python scripts/check_environment.py  # confirms every package is genuinely installed
```

> Why a checker? The brief requires a folder named `streamlit/`. Started from the project root, a bare
> `python -c "import streamlit"` can pick up that folder instead of the library and wrongly look "installed".
> `check_environment.py` guards against this.

### Database

* **SQLite (default, zero setup)**: nothing to do; `data/cart2insights.db` is created automatically.
* **MySQL 8.0+** (the brief's tag): create a user, then in `.env` set
  `DB_BACKEND=mysql`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` (and `DB_HOST`/`DB_PORT` if not local).
  The pipeline creates the database if the user has permission. MySQL 8+ is required for window functions and CTEs.

Credentials live only in `.env` (git-ignored). The code never hardcodes them.

### Data

Download the Cart2Insights dataset (link in the brief) and place the 9 CSVs in `data/raw/`.
File names are matched flexibly (`olist_orders_dataset.csv` or `orders.csv` both work). If a file is missing
or a column is absent, the loader says exactly which.

To rehearse on generated test data instead:
```bash
python scripts/make_synthetic_data.py              # writes data/synthetic/
python run_pipeline.py --raw-dir data/synthetic --synthetic
```
`--synthetic` stamps the database so the dashboard shows a warning banner and the generated insights file
is labelled as test data.

## Dashboard

Sidebar filters (purchase-month range, customer state, product category, Top-N, minimum-orders threshold)
apply to every page.

1. **Business Overview**: revenue, orders, customers, sellers, average order value, average review score
2. **Sales Analysis**: monthly revenue trend and growth, revenue by category, top products, sales by state/city
3. **Customer Analysis**: distribution, spending, repeat vs new, top customers
4. **Seller & Product Analysis**: top sellers, seller revenue and share, category performance, seller ratings
5. **Delivery Analysis**: average delivery time, on-time vs delayed, performance by location, delay vs review score
6. **Customer Experience**: review distribution, reviews by category, rating vs delivery performance
7. **Statistical Tests**: t-test, ANOVA, chi-square with hypotheses, assumption checks, p-values, decisions
8. **Business Insights**: generated Observation → Interpretation → Impact → Recommendation cards
9. **SQL Analysis**: the SQL (joins, subqueries, CTEs, window functions, HAVING, aggregations) with live results

## Key definitions and assumptions

* **Revenue (GMV)** = item price + freight, over *valid sales* (orders with items whose status is not `canceled`/`unavailable`).
* **Customer** = `customer_unique_id` (the `customer_id` column is issued per order). **Repeat customer** = more than one valid-sale order.
* **Delivery days** = delivered date − purchase date; **delivery delay** = delivered date − estimated date (> 0 is late). Only delivered orders with valid dates count.
* **One review per order**: if an order has several reviews, the latest one is kept.
* **Primary category / payment type of an order** = category of its highest-priced item / payment with the largest value.
* The schema assumes the standard 9-table layout (customers, geolocation, order_items, order_payments, order_reviews, orders, products, sellers, category-name translation) with Olist-style column names. **I could not inspect your dataset, so this is an assumption**; the loader fails with a clear message if columns differ.
* Currency symbol on the dashboard is configurable (`CURRENCY_SYMBOL` in `.env`, default `R$`).
* Product-name columns do not exist in this layout, so "top products" are identified by product ID and category.

## Statistical methods

| Test | Method | Assumption handling |
|---|---|---|
| Delay vs review score | Welch two-sample t-test (one-sided, delayed < on time) + Mann-Whitney U | Levene (variance), Shapiro-Wilk (normality; scores are discrete, so CLT + non-parametric check), Cohen's d |
| Category vs order value | One-way ANOVA on log(1+value) + Kruskal-Wallis, Tukey HSD post-hoc | Skewness → log transform, Levene, Shapiro on residuals, η² |
| Payment vs order status | Chi-square test of independence | Rare levels pooled, expected-count check (<5), Cramér's V, standardised residuals |

## Testing

```bash
python tests/test_pipeline.py        # or: python -m pytest tests -q
```

Full results and the honest not-verified list are in `docs/test_results.md`; the requirement-by-requirement status is in `docs/requirements_checklist.md`.

**Verified (on synthetic data, SQLite):** primary-key uniqueness and referential integrity after cleaning;
that injected data problems are detected and fixed; feature definitions; PK/FK enforcement in SQL;
every dashboard query and every SQL-showcase query executes and returns rows; KPIs, category totals,
filters, window-function results cross-checked against Pandas; the t-test p-value matches a direct SciPy
call; insight generation. All 21 tests passed. In addition, the final-presentation deck was generated and visually inspected, all 9 dashboard pages were executed with the UI
libraries stubbed (verifies the data flow and column names), and notebook code cells 01–03 and 06–07 were executed.

**Not verified in the build environment** (Streamlit, SQLAlchemy, PyMySQL, Plotly could not be installed there):
* the real Streamlit rendering (layout, chart appearance, responsiveness on mobile);
* the SQLAlchemy code paths (`src/db.py`, `src/load_to_sql.py`, `streamlit/database.py`), notebooks 04–05, and `run_pipeline.py` as a whole;
* MySQL (schema and queries are written to be portable, but only SQLite was exercised);
* behaviour on the real dataset and its size.

Please run `python run_pipeline.py` and the dashboard once on your machine and report anything that breaks.
